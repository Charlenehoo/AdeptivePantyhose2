v3.0.4 从 v3.0.3 的回归出发，中间经历了 5 个 WIP commit，踩了 7 个坑，其中 3 个是 v3.0.2/v3.0.3 踩过的**同一个坑换了个表现**。这份文档记录每个坑的具体表现、根因、修复方式，以及**防回归的判据**——下一个 AI 接手时，按这些判据快速识别，不要重蹈覆辙。

## 1. 坑 1：`GetAsNiNode` 是伪代码臆造的 API

### 1.1 表现

编译报错：

```
error: no member named 'GetAsNiNode' in 'RE::NiAVObject'
```

### 1.2 根因

AI（我）在伪代码里写了 `a_object->GetAsNiNode()`，以为 `NiAVObject` 有便捷 cast 方法。**CommonLibSSE-NG 的 `RE::NiAVObject` 没有 `GetAsNiNode`，也没有 `GetAsBSGeometry`。**

grep 确认：

```powershell
Get-ChildItem extern\CommonLibSSE\include\RE -Recurse -Filter *.h |
    Select-String -Pattern "GetAsNiNode|GetAsBSGeometry"
```

结果只有 `NiCullingProcess.h` 里的两个虚函数（`GetAsNiNode` / `GetAsBSGeometry`），**是 `NiCullingProcess` 的成员，不是 `NiAVObject` 的**。

`git grep -n "GetAsNiNode" v3.0.3-beta.1` 返回空——v3.0.3 项目代码里从来没有这个方法。

### 1.3 修复

用 `skyrim_cast` 或 RTTI 判断：

```cpp
auto* node = skyrim_cast<RE::NiNode*>(a_object);
```

### 1.4 防回归

**任何 `NiAVObject*` 的 cast 方法，先在 `extern/CommonLibSSE/include/RE/N/NiAVObject.h` 里确认。** 不要凭记忆写。CommonLibSSE-NG 的便捷 cast 是 `skyrim_cast`，不是成员方法。

## 2. 坑 2：`GetRTTI() == RE::NiNode::Ni_RTTI` 类型不匹配

### 2.1 表现

编译报错：

```
error C2679: binary '==': no operator found which takes a right-hand
operand of type 'const REL::ID' (or there is no acceptable conversion)
```

### 2.2 根因

`GetRTTI()` 返回 `const NiRTTI*`，但 `RE::NiNode::Ni_RTTI` 是 `const REL::ID`（地址库 ID），两者不能直接比较。

### 2.3 修复

用 `REL::Relocation` 把 `REL::ID` 解成实际指针：

```cpp
[[nodiscard]] auto NiNodeRTTI() -> const RE::NiRTTI* {
    static const REL::Relocation<const RE::NiRTTI*> s_rtti{RE::NiNode::Ni_RTTI};
    return s_rtti.get();
}
```

### 2.4 防回归

**`REL::ID` 不是指针。** 任何 `RE::Xxx::Ni_RTTI` 都是 `REL::ID`，要比较必须先 `REL::Relocation` 解引用。

## 3. 坑 3：精确 RTTI 匹配漏掉子类（v3.0.3 Bug 1 的另一种表现）

### 3.1 表现

编译通过，但日志里 `[ApplyOther]` **只对裤袜触发**，body / nails / shoes 全部没出现。视觉上“穿高跟看不出脚部变形”。

### 3.2 根因

`a_object->GetRTTI() == NiNodeRTTI()` 只匹配**精确类型 `NiNode`**。body / nails / shoes 的 `partClone` 是 `BSFadeNode` 等子类，`GetRTTI()` 返回的是 `BSFadeNode::Ni_RTTI`，不等于 `NiNode::Ni_RTTI`。

**这正是 v3.0.3 Bug 1 的同一个坑换了个表现**——v3.0.3 是 `HasShapeData` 检查根节点，v3.0.4 WIP 是 RTTI 精确匹配。两者都导致 body mesh 被错误跳过。

### 3.3 修复

用 `skyrim_cast<RE::NiNode*>` 走引擎 RTTI 的继承链：

```cpp
auto* node = skyrim_cast<RE::NiNode*>(a_object);
if (node != nullptr) {
    for (auto& child : node->children) {
        if (child && HasShapeDataRecursive(child.get())) {
            return true;
        }
    }
}
```

### 3.4 防回归

**任何 RTTI 类型判断必须走继承链**，不能 `GetRTTI() == Xxx::Ni_RTTI` 精确比较。`skyrim_cast` 是标准做法；手写 `NiRTTI::parent` 链遍历是备选。

**判据**：如果 `[ApplyOther]` 只对某些 mesh 触发，而对 `bipedData` 里的其他 mesh 不触发，第一时间怀疑 RTTI 精确匹配漏子类。

## 4. 坑 4：`HasShapeData` 依赖 `HasMorphs`，`NoHeel=0` 时永远 false

### 4.1 表现

脱高跟时裤袜没有 morph——视觉上裤袜保持高跟形状（base），没有变成平脚形状。日志：

```
[12:19:11.116] [Equip] gala equipped=false
[12:19:11.116] SetAbsolute(NoHeel=1)      ← 0→1
[12:19:11.122] [Attach] Feet no SHAPEDATA, skip re-apply
（没有 [ApplyOther] 对裤袜）
```

穿高跟时裤袜 attach 的日志：

```
[12:18:36.823] [Attach] 裤袜 no SHAPEDATA, skip re-apply
```

### 4.2 根因

`HasShapeDataRecursive` 检查 `SHAPEDATA` 是否存在。但 `SHAPEDATA` 只在 SKEE 的 `HasMorphs=true` 时创建。

SKEE 的 `BodyMorphMap::HasMorphs(refr)`：

```cpp
for (auto& morph : *this) {
    float morphFactor = g_bodyMorphInterface.GetBodyMorphs(refr, morph.first.c_str());
    if (morphFactor != 0.0f) return true;   // 任一 morph 非零
}
return false;
```

**`NoHeel=0`（穿高跟的常见状态）时 `HasMorphs=false`，SKEE 不创建 `SHAPEDATA`。** 我们的门禁误判“未就绪”，跳过裤袜。脱高跟时 `NoHeel=1`，需要重新应用，但裤袜的 `SHAPEDATA` 不存在（`NoHeel=0` 时没创建），门禁继续 skip——**morph 值变了，但 mesh 没更新**。

**这是 v3.0.3 Bug 1 的第三次表现**：v3.0.3 是 `HasShapeData` 检查根节点，v3.0.4 WIP 早期是 RTTI 精确匹配，v3.0.4 WIP 后期是 `HasShapeData` 依赖 `HasMorphs`。三次都导致 body mesh 被错误跳过。

### 4.3 修复

门禁从 `HasShapeDataRecursive` 改成 `data.partClone->parent != nullptr`：

```cpp
if (data.partClone->parent == nullptr) {
    continue;   // mesh 未 attach，跳过
}
ApplyVertexDiff(a_actor, *data.partClone, false);
```

`parent != nullptr` 意味着 mesh 已挂到场景图，顶点就绪。`ApplyVertexDiff(false)` 的 `!bodyData` 分支会用当前 base 顶点创建 `SHAPEDATA`，应用 morph delta——**`NoHeel=0` 时应用 0 个 delta（base），`NoHeel=1` 时应用 1 的 delta（平脚）**，两种情况都正确。

`AttachListener::OnAttach` 里也去掉门禁——`OnAttach` 本身意味着 mesh 刚 attach，顶点就绪。

### 4.4 关键概念纠正

**`NoHeel=0` 是 base shape，不是“没有应用”。**

`NoHeel` 的 morph target 定义为：**base = 高跟形状，应用 delta = 平脚形状**。

- `NoHeel=0` → 不应用 delta → base（高跟形状）
- `NoHeel=1` → 应用 delta → base + delta（平脚形状）

**穿高跟时看到“没有变化”是正常的**——裤袜就是 base shape，没有 morph delta 要应用。只有 `0→1`/`1→0` 切换才能看到变化。**之前的分析一度把“`NoHeel=0` 时看不出变化”误判为 bug，浪费了一轮排查。**

### 4.5 防回归

**判据**：如果某个 mesh 的 morph 应该变化但视觉没变，按顺序检查：

1. `[Equip]` 是否出现（`TESEquipEvent` 是否触发）
2. `SetAbsolute` 是否执行（morph 值是否写入）
3. `[ApplyOther]` / `[ApplyOne]` 是否对目标 mesh 出现（mesh 是否被处理）
4. **`HasShapeData` 或 `HasMorphs` 是否是门禁**——如果是，怀疑“morph 值全 0 时 `SHAPEDATA` 不存在”导致的误判
5. `skee.log` 里 `MorphFileCache::ApplyMorphs` 是否对目标 mesh 执行（`BODYTRI` 是否存在，mesh 名字是否匹配）

**任何“检查 mesh 是否就绪”的门禁，不能用 `SHAPEDATA`**——`SHAPEDATA` 的存在依赖 `HasMorphs`，和“mesh 是否就绪”是正交的。用 `parent != nullptr` 或 `lastUpdatedFrameCounter` 之类的“mesh 已挂到场景图”信号。

## 5. 坑 5：`GetWornArmor` 旧值过滤方案失败（v3.0.4 WIP 中间尝试）

### 5.1 表现

第一次尝试把 `UpdateModelWeight` 移回 `TESEquipEvent` 栈，用 `GetWornArmor` 旧值集合过滤。**视觉上完全没有 morph**。日志：

- `[ApplyOther]` 在 `[Equip]` 之后、`[Attach]` 之前出现，位置正确
- `ApplyVertexDiff(false)` 被调用了
- 但视觉无效果

### 5.2 根因（未完全确认，但方向明确）

`TESEquipEvent` 期间 `bipedData->partClone` 可能指向**未就绪的 mesh**——引擎已经在 `TESEquipEvent` 之前或期间部分更新了 `bipedData`，`BODYTRI` 还没加载。`ApplyVertexDiff(false)` 内部 `VisitObjects` 找 `BODYTRI` 失败，`fileCache` 为 null，静默失败。

**关键教训**：**`GetWornArmor` 返回旧值 ≠ `bipedData->partClone` 就绪**。这是两个独立数据源。`TESEquipEvent` 栈不是安全的“mesh 就绪”信号。

### 5.3 修复

这个失败尝试直接导致了 v3.0.4 最终方案（SSOT 重构）的诞生——放弃“在 `TESEquipEvent` 栈里模拟 `UpdateModelWeight`”，改用 `OnAttach` 作为 SSOT。

### 5.4 防回归

**判据**：如果 `[ApplyOther]` 出现但视觉无效，检查：

1. `partClone->parent` 是否非 null（mesh 是否已 attach）
2. `skee.log` 里 `MorphFileCache::CacheFile` 是否对该 mesh 执行（`BODYTRI` 是否找到）
3. `MorphFileCache::CacheFile` 是否 `fileCache` 为 null（`BODYTRI` 字符串匹配失败）

**不要用“事件期间 `GetWornArmor` 返回旧值”推断“`bipedData->partClone` 也返回旧值”。** 两者是独立数据源，时序不一定同步。

## 6. 坑 6：Modex 的 `AddWornItem` 不触发 `TESEquipEvent`

### 6.1 表现

Modex 三件同穿后：

- `AdeptivePantyhose.log` 里零条 `[Equip]`
- `skee.log` 里 `BodyMorphInterface::OnAttach` 对三件 mesh 各触发一次
- 视觉上三件都 attach 了，但 morph 值没更新（`SetAbsolute` 没执行）
- 如果之前 `NoHeel=1`（脱装备后的默认状态），穿高跟后 `NoHeel` 保持 1，裤袜保持平脚形状——**视觉错误**

### 6.2 根因

Modex 的 `Commands.h:548` 用的是：

```cpp
actor->AddWornItem(equipObject, 1, false, 0, 0);
```

`Actor::AddWornItem` 是底层 API：直接修改 `InventoryEntryData` 的 `ExtraWorn` 标志，**不经过 `ActorEquipManager` 的事件派发路径**。所以 `TESEquipEvent` 不触发，但 mesh 会 attach（引擎下一帧重新构建 mesh）。

**脱装备路径不同**：Modex 的 `UnequipObject`（`Commands.h:464`）走 `ActorEquipManager`，触发 `TESEquipEvent`。所以脱装备有 `[Equip]`，穿装备没有。

### 6.3 修复

`OnAttach` 作为 SSOT 入口，在 `OnAttach` 里主动调用 `EvaluateRules`：

```cpp
void AttachListener::OnAttach(...) {
    // 1) 为当前装备求值（覆盖 Modex 不触发 TESEquipEvent 的情况）
    MorphRuleEngine::GetSingleton().EvaluateRules(actor, a_armor, true);
    // 2) 对当前 mesh 以 isAttaching=false 补一次（幂等）
    skee.ApplyVertexDiff(*a_refr, *a_object, false);
}
```

### 6.4 防回归

**判据**：如果某个 MOD 的装备操作“视觉上看不出变化”，先确认：

1. `AdeptivePantyhose.log` 里有没有 `[Equip]`
2. 没有 → MOD 不触发 `TESEquipEvent`，`OnAttach` 是唯一兜底
3. 有 → 问题在别处

**任何依赖 `TESEquipEvent` 的逻辑，必须确认 MOD 是否走标准 API。** `Actor::EquipItem` / `ActorEquipManager::EquipObject` 触发；`Actor::AddWornItem` 不触发。Papyrus 的 `EquipItem` 走标准路径，触发。

## 7. 坑 7：`NoHeel` 的视觉载体只有裤袜

### 7.1 表现

很长一段时间误判“脚部不变形”是 bug，排查了 `Feet` 的 TRI 内容、`bipedData` 的 `data.item` 是否为 null、`SkinNaked` 是否在 `oldArmors` 里——**全部是无效排查**。

### 7.2 根因

从 `skee.log` 确认各 mesh 的 TRI 内容：

| mesh                        | TRI 内容                                   | 含 `NoHeel` |
| --------------------------- | ------------------------------------------ | ----------- |
| 裤袜 `cpb_s.tri`            | `NoHeel` 3368 顶点                         | ✅          |
| 裸足 `femalefeet.tri`       | `AnkleSize` + `FeetFeminine`               | ❌          |
| 鞋的 Feet `gala_heelsa.tri` | `AnkleSize` + `FeetFeminine` + `Heel`      | ❌          |
| toenails `cpb_nails.tri`    | `NailsLong` + `NailsSharp` + `NailsBuffer` | ❌          |

**`NoHeel` 的唯一视觉载体是裤袜。** 裸足、鞋、toenails 的 TRI 里都没有 `NoHeel` 这个 morph target。

**脚部变形由鞋的 `Heel` morph 控制**（`gala_heelsa.tri` 的 Feet TriShape 有 `Heel`），由 RaceMenu High Heel 系统设置，不是我们的 `NoHeel`。

### 7.3 修复

不需要修复。这是物理事实，不是代码 bug。

### 7.4 防回归

**判据**：任何“某个 mesh 不响应某个 morph”的问题，先确认：

1. `skee.log` 里该 mesh 的 TRI 是否包含该 morph target
2. 不包含 → 不是 bug，是 mesh 作者没在 BodySlide 里 build 这个 morph
3. 包含 → 问题在代码

**不要假设“所有 body mesh 都响应所有 morph”**。`NoHeel` 只影响裤袜，`Heel` 由鞋 + RaceMenu 控制，`NailsLong` 只影响 toenails。

## 8. 三次同一个坑：body mesh 被错误跳过

| 版本            | 门禁                           | 表现                        | 根因                                                     |
| --------------- | ------------------------------ | --------------------------- | -------------------------------------------------------- |
| v3.0.3          | `HasShapeData(data.partClone)` | toenails 浮动               | `SHAPEDATA` 在子 geometry 上，检查根节点永远 false       |
| v3.0.4 WIP 早期 | `GetRTTI() == NiNode::Ni_RTTI` | body/nails/shoes 全部被跳过 | 精确 RTTI 匹配漏掉 `BSFadeNode` 等子类                   |
| v3.0.4 WIP 后期 | `HasShapeDataRecursive`        | 脱高跟时裤袜不变形          | `HasShapeData` 依赖 `HasMorphs`，`NoHeel=0` 时永远 false |

**三次都是“检查 mesh 是否就绪”的门禁出错，且都影响 body mesh。**

### 8.1 唯一正确的门禁：`partClone->parent != nullptr`

| 门禁                      | 优点                                            | 缺点                                              |
| ------------------------- | ----------------------------------------------- | ------------------------------------------------- |
| `HasShapeData`            | 直接反映 SKEE 是否处理过                        | 依赖 `HasMorphs`，`NoHeel=0` 时误判               |
| RTTI 精确匹配             | 简单                                            | 漏子类                                            |
| `parent != nullptr`       | mesh 已挂到场景图 = 顶点就绪；正交于 morph 状态 | 需要 `NiAVObject::parent` 字段（CommonLibSSE 有） |
| `lastUpdatedFrameCounter` | 可判断“本帧是否更新过”                          | 需要额外逻辑                                      |

**判据**：`parent != nullptr` 是唯一正确的“mesh 就绪”信号。不要用 `SHAPEDATA`（依赖 `HasMorphs`），不要用 RTTI 精确匹配（漏子类）。

## 9. 防回归检查清单

### 9.1 编译前

- [ ] 任何 `NiAVObject*` 的 cast 方法，先在 `extern/CommonLibSSE/include/RE/N/NiAVObject.h` 确认存在
- [ ] 任何 `RE::Xxx::Ni_RTTI` 与 `GetRTTI()` 比较，必须经 `REL::Relocation` 解引用
- [ ] 任何 RTTI 类型判断，必须走继承链（`skyrim_cast` 或 `NiRTTI::parent`）

### 9.2 运行时日志检查

| 症状                                             | 可能原因                                      | 检查点                                                       |
| ------------------------------------------------ | --------------------------------------------- | ------------------------------------------------------------ |
| `[ApplyOther]` 零条或只对部分 mesh               | 门禁误判                                      | `parent != nullptr` 是否正确                                 |
| `[ApplyOther]` 对某 mesh 出现但视觉无变化        | 该 mesh 的 TRI 没有目标 morph，或 mesh 未就绪 | `skee.log` 的 `MorphFileCache::CacheFile` 是否包含目标 morph |
| 某 MOD 穿装备后视觉无变化                        | MOD 不触发 `TESEquipEvent`                    | `[Equip]` 是否出现；`OnAttach` 是否触发                      |
| 脱装备后某 mesh 不响应                           | 门禁误判或 mesh 已 detach                     | `parent` 是否非 null；`[ApplyOther]` 是否对该 mesh 出现      |
| 同一 node 的 `Impl_ApplyVertexDiff` 出现两次以上 | double application                            | `isAttaching` 是否误用 `true` 而非 `false`                   |

### 9.3 关键概念澄清（避免误判）

| 概念                | 正确理解                                   | 常见误判               |
| ------------------- | ------------------------------------------ | ---------------------- |
| `NoHeel=0`          | base shape（高跟形状），不是“没有应用”     | 误判为“morph 未生效”   |
| `HasMorphs=false`   | 所有 morph 值都是 0，SKEE 不创建 SHAPEDATA | 误判为“mesh 未就绪”    |
| `SHAPEDATA` 不存在  | 可能未就绪，也可能 `HasMorphs=false`       | 误判为“未就绪”         |
| `parent == nullptr` | mesh 未 attach 或已 detach                 | 唯一的“未就绪”判据     |
| `AddWornItem`       | 不触发 `TESEquipEvent`                     | 误判为“事件丢失”       |
| 脚部变形            | 由鞋的 `Heel` + RaceMenu 控制              | 误判为 `NoHeel` 的职责 |

## 10. 关键设计原则（避免重蹈覆辙）

1. **`OnAttach` 栈只应处理当前 mesh**，不应处理其他 mesh 的 morph 重应用。
2. **`OnAttach` 里调 `ApplyVertexDiff(false)` 而不是 `true`**——`false` 是“重置到 `SHAPEDATA` 再应用”，幂等；`true` 是“在当前顶点上再应用”，double application。
3. **`OnEquipEvent` 栈里只处理旧装备**，不碰正在 attach 的装备。
4. **“mesh 就绪”的唯一正确门禁是 `partClone->parent != nullptr`**，不是 `HasShapeData`（依赖 `HasMorphs`），不是 RTTI 精确匹配（漏子类）。
5. **`SHAPEDATA` 在子 geometry 上，不在根节点上**。任何 `HasShapeData` 检查必须递归。
6. **`GetWornArmor` 返回值 ≠ `bipedData->partClone` 的就绪状态**。独立数据源。
7. **`NoHeel=0` 是 base shape，不是“没有应用”**。穿高跟时看不到变化是正常的。
8. **`NoHeel` 的唯一视觉载体是裤袜**。不要假设“所有 body mesh 都响应所有 morph”。
9. **`Actor::AddWornItem` 不触发 `TESEquipEvent`**。任何依赖 `TESEquipEvent` 的逻辑必须有 `OnAttach` 兜底。
10. **`REL::ID` 不是指针**。任何 `RE::Xxx::Ni_RTTI` 与 `GetRTTI()` 比较，必须经 `REL::Relocation` 解引用。
