## 1. 一句话

`TESEquipEvent` 不是装备变化的 SSOT——Modex 的 `Actor::AddWornItem` 路径不触发它。**唯一绕不过的信号是 `IAddonAttachmentInterface::OnAttach`（mesh attach）。** v3.0.4 把 `OnAttach` 作为求值 + 当前 mesh 更新的入口，`OnEquipEvent` 退化为“旧 mesh 响应新 morph”的补充路径。

## 2. 背景：v3.0.2 → v3.0.3 → v3.0.4 的演进

### 2.1 v3.0.2（稳定基线）

`OnEquipEvent` 里 `SetAbsolute` 后同步调 `UpdateModelWeight`。遍历 `bipedData` 全部 mesh。

**已知 bug**：首次同帧穿脚趾甲 + 裤袜时，`TESEquipEvent` 时新 mesh 未 attach 就绪，`UpdateModelWeight` 为未就绪 mesh 创建错误 `SHAPEDATA`，脚趾甲闪烁后消失。初始化后稳定。

### 2.2 v3.0.3（方案 B，已发布，有回归）

**设计动机**：让当前 mesh 的 `SHAPEDATA` 在 mesh 就绪之后创建。`OnAttach` 是“mesh 就绪”的唯一可靠信号，因此把当前 mesh 的初始化放到 `OnAttach` 里。SKEE 自己的 `BodyMorphInterface::OnAttach` 本来就在做这件事（`isAttaching=true`），我们只加兜底。

**实现**：

- `OnEquipEvent` 只 `SetAbsolute`，不调 `UpdateModelWeight`
- 新增 `AttachListener`（实现 `IAddonAttachmentInterface`），在 `kPostPostLoad` 注册到 SKEE 的 `IActorUpdateManager`（追加到 vector 末尾，晚于 SKEE 自己的观察者）
- `OnAttach` 里：
  - 当前 mesh：SKEE `BodyMorphInterface::OnAttach`（`isAttaching=true`）或我们的 `ApplyVertexDiffCurrentMesh` 兜底
  - 其他已存在 mesh：`ApplyVertexDiffToWornMeshes` 遍历 `bipedData`，用 `HasShapeData(partClone)` 门禁，`isAttaching=false`

**修复了**：首次同帧穿脚趾甲 + 裤袜（已视觉验证）

**引入了两个回归**（用户评价“3.0.2 better than 3.0.3”）：

| Bug                 | 表现                                        | 根因                                                                                             |
| ------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Bug 1（rudeboybox） | 平底足 toenails 后穿 sandals，toenails 浮动 | `HasShapeData(partClone)` 检查根节点，`SHAPEDATA` 在子 geometry 上，永远 false，toenails 被 skip |
| Bug 2（另一用户）   | OAR - IED Conditions 冲突                   | v3.0.3 把 D3D 操作移进了 `AttachBipedObject` hook 栈，与 IED 的 D3D hook 交错                    |

### 2.3 v3.0.4 WIP 中间的失败尝试（**重要探索教训**）

**第一次尝试：把 `UpdateModelWeight` 移回 `TESEquipEvent` 栈，用 `GetWornArmor` 旧值集合过滤**

**思路**：`DoUpdate(e)` = `ApplyVertexDiff(refr, e, false)`。`UpdateModelWeight` 等价于“对 `bipedData` 所有 mesh + attachment holder 各调一次 `ApplyVertexDiff(false)`”。我们做同样的事，但用 `oldArmors` 集合过滤，天然排除当前装备（`GetWornArmor` 在 `TESEquipEvent` 期间返回旧值）。

**实现**（已提交，后回滚/改进）：

```cpp
// OnEquipEvent
std::unordered_set<RE::FormID> oldArmors;
for (std::uint32_t slot = 0; slot < kBipedSlotBitCount; ++slot) {  // =32
    const auto slotBit = static_cast<RE::BGSBipedObjectForm::BipedObjectSlot>(1U << slot);
    if (auto* worn = a_actor->GetWornArmor(slotBit); worn != nullptr) {
        oldArmors.insert(worn->GetFormID());
    }
}
if (a_armor != nullptr) oldArmors.erase(a_armor->GetFormID());  // 卸下排除
// ... EvaluateAndApply ...
if (anyApplied) {
    SKEEIntegration::GetSingleton().ApplyVertexDiffToWornMeshes(*a_actor, oldArmors);
}
```

**实测结果**：**视觉上完全没有 morph**。日志显示 `[ApplyOther]` 确实在 `[Equip]` 之后、`[Attach]` 之前出现，位置正确，`ApplyVertexDiff(false)` 被调用了，但视觉无效果。

**根因分析（未完全确认，但方向明确）**：`TESEquipEvent` 期间 `bipedData->partClone` 可能指向**未就绪的 mesh**（引擎已经在 `TESEquipEvent` 之前或期间部分更新了 `bipedData`，`BODYTRI` 还没加载），`ApplyVertexDiff(false)` 内部 `VisitObjects` 找 `BODYTRI` 失败，`fileCache` 为 null，静默失败。

**关键教训**：**`GetWornArmor` 返回旧值 ≠ `bipedData->partClone` 就绪**。这是两个独立数据源。`TESEquipEvent` 栈不是安全的“mesh 就绪”信号。这个失败尝试直接导致了 v3.0.4 最终方案（SSOT 重构）的诞生。

### 2.4 v3.0.4 最终方案（SSOT 重构）

**核心决策**：`TESEquipEvent` 不是装备变化的 SSOT——Modex 的 `Actor::AddWornItem` 路径不触发它。**唯一绕不过的信号是 `IAddonAttachmentInterface::OnAttach`（mesh attach）。**

把 `OnAttach` 作为**求值 + 当前 mesh 更新的入口**，`OnEquipEvent` 退化为“旧 mesh 响应新 morph”的补充路径。

## 3. 两条路径的精确职责

| 路径               | 触发源              | 时机           | 处理的 mesh                                                    |
| ------------------ | ------------------- | -------------- | -------------------------------------------------------------- |
| **`OnEquipEvent`** | `TESEquipEvent`     | 事件派发期间   | **其他已存在的 mesh**（`bipedData` 里 `parent != nullptr` 的） |
| **`OnAttach`**     | `AttachBipedObject` | mesh attach 后 | **当前刚 attach 的 mesh**                                      |

**两条路径都求值**（`EvaluateRules` 幂等），保证无论哪条路径触发，morph 值都被设置。但 mesh 更新各管各的：

- `OnAttach` **只碰当前装备**，不碰其他 mesh（v3.0.3 Bug 1/Bug 2 的教训）
- `OnEquipEvent` **只碰旧装备**，不碰正在 attach 的装备

## 5. 关键设计决策

### 5.1 为什么 `OnAttach` 必须调 `ApplyVertexDiff(false)`，不能只求值

SKEE 的 `BodyMorphInterface::OnAttach` 在 observer 顺序中**先于我们**（SKEE 在 `Load` 阶段注册，我们在 `kPostPostLoad` 注册，追加到 vector 末尾）。SKEE 用 `isAttaching=true` 处理过：

- `HasMorphs=true` 时：用当前顶点创建 `SHAPEDATA` + 应用 morph
- `HasMorphs=false` 时：什么都不做

**但 SKEE 用的是 `SetAbsolute` 之前的旧 morph 值**（Modex 的 `AddWornItem` 不触发 `TESEquipEvent`，我们的 `EvaluateRules` 在 `OnAttach` 里才第一次执行）。**如果只求值不重应用，mesh 保持旧值，视觉上“看不到变化”**。

`isAttaching=false` 的语义：重置到 `SHAPEDATA`（base），再应用 morph。因为 `SHAPEDATA` 刚由 SKEE 用正确 base 创建（或由我们的 `!bodyData` 分支用当前 base 顶点创建），重置后结果是确定的。**幂等，不是 v3.0.3 的 double application。**

| 调用                  | `isAttaching` | 行为                                             |
| --------------------- | ------------- | ------------------------------------------------ |
| SKEE `OnAttach`       | `true`        | 用当前顶点创建 SHAPEDATA → 应用 morph            |
| v3.0.3 `ApplyCurrent` | `true`        | **不重置**，在当前顶点上再应用一次 → 双重变形 ❌ |
| v3.0.4 `OnAttach`     | `false`       | **重置**到 SHAPEDATA → 应用 morph → 幂等 ✅      |

### 5.2 为什么门禁用 `partClone->parent` 而不是 `HasShapeData`

**`HasShapeData` 依赖 SKEE 的 `HasMorphs`，方向错了。**

SKEE 的 `BodyMorphMap::HasMorphs(refr)` 逻辑：

```cpp
for (auto& morph : *this) {
    float morphFactor = g_bodyMorphInterface.GetBodyMorphs(refr, morph.first.c_str());
    if (morphFactor != 0.0f) return true;   // 任一 morph 非零才返回 true
}
return false;
```

`NoHeel=0`（穿高跟的常见状态）时 `HasMorphs=false`，SKEE 的 `OnAttach` 不创建 `SHAPEDATA`。我们的 `HasShapeDataRecursive` 也返回 false，裤袜被跳过——**脱高跟时 `NoHeel 0→1` 需要重新应用，但被门禁误杀**。

**`SHAPEDATA` 不存在有两个原因**：

1. **mesh 未就绪**（v3.0.2 的 bug 路径）：`ApplyVertexDiff(false)` 走 `!bodyData` 分支用错误顶点创建 `SHAPEDATA`，永久固化
2. **`HasMorphs=false`**（所有 morph 值都是 0）：SKEE 没创建 `SHAPEDATA`，但 mesh 已就绪，`!bodyData` 分支用当前 base 顶点创建 `SHAPEDATA`——**正确**

**区分这两个场景的信号是 `partClone->parent`**：

- `parent != nullptr`：mesh 已挂到场景图，顶点就绪
- `parent == nullptr`：mesh 未 attach 或已 detach

| 场景                            | `parent` | 修复前（`HasShapeData`）                | 修复后（`parent`）                                    |
| ------------------------------- | -------- | --------------------------------------- | ----------------------------------------------------- |
| 穿高跟裤袜 attach（`NoHeel=0`） | 非 null  | 跳过（错，但 base 就是高跟，看不出）    | 处理 → 创建 SHAPEDATA（base）+ 应用 delta=0 → base ✅ |
| 脱高跟裤袜重应用（`NoHeel=1`）  | 非 null  | **跳过（错，裤袜保持 base，视觉错误）** | 处理 → 创建 SHAPEDATA（base）+ 应用 delta=1 → 平脚 ✅ |
| 同帧穿新装备（未 attach）       | **null** | 可能 true/false                         | 跳过 ✅                                               |

### 5.3 为什么 `UpdateModelWeight` 只剩读档一个用户

| 场景                       | 用什么                                | 原因                                                                                                                                                         |
| -------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `OnEquipEvent`             | `ApplyVertexDiffToWornMeshes`         | `TESEquipEvent` 期间 `bipedData` 可能已有未 attach 的新 mesh，`UpdateModelWeight` 会对它创建错误 `SHAPEDATA`（v3.0.2 bug）。`parent` 门禁精确跳过未就绪 mesh |
| `AttachListener::OnAttach` | `ApplyVertexDiff(false)`（单个 mesh） | 只处理当前 mesh，不碰其他 mesh（v3.0.3 教训）                                                                                                                |
| `OnActorLoaded`（读档）    | `UpdateModelWeight`                   | 读档后 mesh 已就绪，不在任何 hook 栈里；且它**额外处理 attachment holder**（SKEE `AttachmentInterface` 挂的动态 mesh，不在 `bipedData` 里）                  |

**不统一去掉 `UpdateModelWeight` 的原因**：会失去 attachment holder 覆盖，需要额外写 skeleton 遍历找 `NiAttachments [NiOA]`。当前读档没有 bug 报告，保留是“最小惊讶”的选择。

## 6. 完整时序

### 6.1 游戏内标准穿装备（`TESEquipEvent` 触发）

```
TESEquipEvent → OnEquipEvent:
  - EvaluateRules → SetAbsolute
  - ApplyVertexDiffToWornMeshes（处理旧 mesh）
OnAttach:
  - EvaluateRules → SetAbsolute（幂等重复）
  - ApplyVertexDiff(false)（当前 mesh，幂等）
```

求值两次，无害。旧 mesh 被 `ApplyOther` 重应用，新 mesh 被 `OnAttach` 处理。

### 6.2 Modex 穿装备（`TESEquipEvent` 不触发）

```
（无 TESEquipEvent）
OnAttach:
  - EvaluateRules → SetAbsolute  ← 唯一的一次求值
  - ApplyVertexDiff(false)       ← 唯一的一次 mesh 更新
```

**每个新 mesh 的 `OnAttach` 各自求值 + 处理当前 mesh。** 三件同穿时三件都正确，因为没有“旧 mesh 需要更新”的场景（三件都是新装备）。

### 6.3 Modex 脱装备（`TESEquipEvent` 触发）

```
TESEquipEvent(equipped=false) → OnEquipEvent:
  - EvaluateRules → SetAbsolute
  - ApplyVertexDiffToWornMeshes：
    - 已 detach 的 mesh（parent=null）跳过
    - 还留着的 mesh（如只脱鞋保留裤袜）→ ApplyVertexDiff(false)
```

**“只脱鞋保留裤袜”场景**：裤袜在 `bipedData` 里，`parent != nullptr`，被 `ApplyVertexDiff(false)` 重应用 `NoHeel=1`（平脚）。正确。

## 7. 关键技术事实（已确认）

### 7.1 SKEE `ApplyVertexDiff` 语义

接口：`ApplyVertexDiff(TESObjectREFR* refr, NiAVObject* rootNode, bool erase = false)`，实现里形参名叫 `attach`，最终传给 `MorphCache::ApplyMorphs(refr, rootNode, isAttaching, true)`。

`isAttaching` 控制两条分支：

- **`true`**（attach 中）：跳过 `SHAPEDATA` 重置；`!SHAPEDATA` 时用**当前顶点**创建基准；应用 morph
- **`false`**（已存在 mesh 重新应用）：用已有 `SHAPEDATA` 重置到 base；应用 morph
- **危险路径**：对未就绪 mesh 调 `false`，`!SHAPEDATA` 时用**当前可能错误的顶点**创建基准，永久固化

`SHAPEDATA` 是挂在**子 geometry（`BSGeometry`）**上的 `NiBinaryExtraData`，不是根节点上。检查根节点是否有 `SHAPEDATA` **永远返回 false**。

### 7.2 `UpdateModelWeight` 的精确拆解

```
UpdateModelWeight(refr, immediate=false)
→ Impl_UpdateModelWeight: new NIOVTaskUpdateModelWeight, g_task->AddTask（主线程同步）
→ NIOVTaskUpdateModelWeight::Run → ApplyBodyMorphs(actor, false)
→ Impl_ApplyBodyMorphs → morphCache.UpdateMorphs(refr, false)
→ MorphCache::UpdateMorphs:
    VisitBipedNodes(refr, λ) {
        ApplyMorphs(refr, object, isAttaching=false, deferUpdate)   // 对每个 biped mesh
    }
    VisitSkeletalRoots: attachment holder 也 ApplyMorphs
→ MorphCache::ApplyMorphs → MorphFileCache::ApplyMorphs
    每个 shape: ApplyMorph → DeepCopy skinPartition → SHAPEDATA 重置/创建 → 应用 delta
    defer = (*g_main)->threadId != GetCurrentThreadId()   // 参数被覆盖
    主线程下 NIOVTaskUpdateSkinPartition::Run() 同步执行（D3D 操作）
```

**关键结论**：`UpdateModelWeight` 在主线程下完全同步，D3D 操作立即发生。`ApplyVertexDiff(refr, mesh, false)` 等价于对单个 mesh 做 `UpdateModelWeight` 循环体里的事——两者最终都走 `MorphFileCache::ApplyMorphs`，路径相同。

### 7.3 `GetWornArmor` 在 `TESEquipEvent` 期间返回旧值（已确认）

穿上事件：`GetWornArmor` 不含正在穿的 armor。卸下事件：含正在卸下的 armor。这是报告 §7.7 和多次日志验证的事实。

**但**：`GetWornArmor` 和 `bipedData->object` 是**两个独立数据源**。`GetWornArmor` 返回旧值 ≠ `bipedData->partClone` 也是旧值/就绪状态。这是 v3.0.4 WIP 中间失败尝试的根因。

### 7.4 `bipedData` 字段映射（CommonLibSSE-NG AE）

| SKEE 1.5.97             | CommonLibSSE-NG AE                          |
| ----------------------- | ------------------------------------------- |
| `bipedData->unk10[i]`   | `weightModel->objects[i]`                   |
| `bipedData->unk13C0[i]` | `weightModel->bufferedObjects[i]`           |
| `data.armor`            | `data.item`（`TESForm*`）                   |
| `data.object`           | `data.partClone`（`NiPointer<NiAVObject>`） |
| `42`                    | `RE::BIPED_OBJECTS::kTotal`                 |

`BipedObjectSlot` 是位标志枚举，`kFX01 = 1U << 31`，共 32 个有效位。`GetWornArmor` 只接受这 32 个。`BIPED_OBJECTS::kTotal = 42` 是 `bipedData` 数组长度，包含索引 32..41 的额外槽位。

### 7.5 `NoHeel` 的视觉载体

从 `skee.log` 确认：

| mesh                        | TRI 内容                                   | 含 `NoHeel` |
| --------------------------- | ------------------------------------------ | ----------- |
| 裤袜 `cpb_s.tri`            | `NoHeel` 3368 顶点                         | ✅          |
| 裸足 `femalefeet.tri`       | `AnkleSize` + `FeetFeminine`               | ❌          |
| 鞋的 Feet `gala_heelsa.tri` | `AnkleSize` + `FeetFeminine` + `Heel`      | ❌          |
| toenails `cpb_nails.tri`    | `NailsLong` + `NailsSharp` + `NailsBuffer` | ❌          |

**`NoHeel` 的唯一视觉载体是裤袜。** 脚部变形由鞋的 `Heel` morph 控制（RaceMenu High Heel 系统），不是我们的 `NoHeel`。

### 7.6 `NoHeel=0` 是 base shape，不是“没有应用”

`NoHeel` 的 morph target 定义为：**base = 高跟形状，应用 delta = 平脚形状**。

- `NoHeel=0` → 不应用 delta → base（高跟形状）
- `NoHeel=1` → 应用 delta → base + delta（平脚形状）

**穿高跟时看到“没有变化”是正常的**——裤袜就是 base shape，没有 morph delta 要应用。只有 `0→1`/`1→0` 切换才能看到变化。

### 7.7 Modex 的 `AddWornItem` 不触发 `TESEquipEvent`

Modex 的 `Commands.h:548` 用的是：

```cpp
actor->AddWornItem(equipObject, 1, false, 0, 0);
```

`Actor::AddWornItem` 是底层 API：直接修改 `InventoryEntryData` 的 `ExtraWorn` 标志，**不经过 `ActorEquipManager` 的事件派发路径**。所以 `TESEquipEvent` 不触发，但 mesh 会 attach（引擎下一帧重新构建 mesh）。

脱装备路径（`ActorEquipManager::UnequipObject`）触发 `TESEquipEvent`。所以脱装备有 `[Equip]`，穿装备没有。

### 7.8 `REL::ID` 不是指针

`RE::Xxx::Ni_RTTI` 是 `REL::ID`，不是 `const NiRTTI*`。要比较必须先 `REL::Relocation` 解引用：

```cpp
[[nodiscard]] auto NiNodeRTTI() -> const RE::NiRTTI* {
    static const REL::Relocation<const RE::NiRTTI*> s_rtti{RE::NiNode::Ni_RTTI};
    return s_rtti.get();
}
```

且任何 RTTI 类型判断必须走继承链（`skyrim_cast` 或 `NiRTTI::parent`），不能 `GetRTTI() == Xxx::Ni_RTTI` 精确比较——会漏掉 `BSFadeNode` 等子类。

| v3.0.4 WIP 后期 | `HasShapeDataRecursive`        | 脱高跟时裤袜不变形          | `HasShapeData` 依赖 `HasMorphs`，`NoHeel=0` 时永远 false |

**三次都是“检查 mesh 是否就绪”的门禁出错，且都影响 body mesh。** 唯一正确的门禁是 `partClone->parent != nullptr`（mesh 已挂到场景图 = 顶点就绪；正交于 morph 状态）。

详见 `v3.0.4-pitfalls-and-regression-guards.md` §7。

## 10. 已知边界

### 10.1 Modex 三件同穿的 attach 顺序依赖

`OnAttach` 只处理当前 mesh。如果新装备影响了已有 mesh 的 morph 值，已有 mesh 不会被更新。

**示例**：Modex 三件同穿，attach 顺序是“裤袜先、高跟后”：

1. 裤袜 attach：`NoHeel` 保持脱装备后的旧值 1，裤袜的 `SHAPEDATA` 用 `NoHeel=1` 创建（base = 平脚形状）
2. 高跟 attach：`NoHeel` 0→0，但**高跟的 `OnAttach` 只处理高跟自己，不处理裤袜**
3. 裤袜保持平脚形状——**视觉错误**

**本地测试恰好是安全顺序**：toenails → 高跟 → 裤袜（裤袜最后 attach，看到的 `NoHeel=0`）。

**需要 rudeboybox 按反序复测**：shoes → hosiery → toenails。

如果失败，备选方案（按优先级）：

| 方案                                                                                   | 代价                   |
| -------------------------------------------------------------------------------------- | ---------------------- |
| A：接受限制，文档说明“按 toenails → hosiery → shoes 顺序”                              | 零，但用户教育成本     |
| B：`OnAttach` 求值后，如果 morph 值有变化，用 SKSE Task 延迟到下一帧对所有 mesh 重应用 | 一帧视觉延迟，可能闪烁 |
| C：回到 v3.0.3 的“对其他 mesh 操作”，但改进门禁和 D3D 时机                             | 有 IED 冲突风险        |

**当前选 A**，等 rudeboybox 反馈。

### 10.2 性能：每条 `[Equip]` 处理 9 个 mesh

三件同脱时 6 条 `[Equip]`，每条处理 9 个 mesh（第一人称 + 第三人称 + bufferedObjects），共 54 次 `ApplyVertexDiff(false)`。每次都是 D3D 同步操作。虽然幂等，但 `D3D11DeviceContext` 调用不便宜。

**不阻塞当前版本**。如果用户报告卡顿，可以加“本帧已处理过这个 mesh”的集合避免重复。

### 10.3 `NoHeel` 的唯一视觉载体是裤袜

见 §7.5。“脱装备后看不到变化”在物理上是正确的，不是 bug。脚部变形由鞋的 `Heel` morph 控制（RaceMenu High Heel 系统），不是我们的 `NoHeel`。

### 10.4 `NoHeel=0` 是 base shape

见 §7.6。穿高跟时看到“没有变化”是正常的——裤袜就是 base shape。

## 11. 与 v3.0.2/v3.0.3 的精确对比

| 维度              | v3.0.2                         | v3.0.3                                   | v3.0.4                                                      |
| ----------------- | ------------------------------ | ---------------------------------------- | ----------------------------------------------------------- |
| 求值入口          | `OnEquipEvent`                 | `OnEquipEvent` + `OnAttach` 兜底         | `OnEquipEvent` + `OnAttach`（幂等）                         |
| 当前 mesh 更新    | `UpdateModelWeight` 全量       | `OnAttach` 里 `ApplyVertexDiff(true)`    | `OnAttach` 里 `ApplyVertexDiff(false)`                      |
| 其他 mesh 更新    | `UpdateModelWeight` 全量       | `OnAttach` 里遍历 `BipedAnim`            | `OnEquipEvent` 里 `ApplyVertexDiffToWornMeshes`             |
| 未就绪 mesh       | 错误 `SHAPEDATA`（v3.0.2 bug） | `HasShapeData` skip（漏更新 toenails）   | `parent` 门禁精确跳过                                       |
| D3D 栈            | `TESEquipEvent`                | **`AttachBipedObject` hook**（IED 冲突） | `OnAttach` 只处理当前 mesh；其他 mesh 在 `TESEquipEvent` 栈 |
| `NoHeel=0` 时裤袜 | 保持 base（正确）              | `HasShapeData` skip（无影响）            | 处理，创建 SHAPEDATA（base）                                |
| 脱高跟时裤袜      | `UpdateModelWeight` 处理       | `HasShapeData` skip（**错误**）          | `ApplyVertexDiff(false)` 正确处理                           |
| Modex 穿装备      | 不触发 `TESEquipEvent`，不工作 | 不工作（`OnAttach` 没求值）              | `OnAttach` 求值 + 应用                                      |
