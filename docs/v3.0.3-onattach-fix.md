# v3.0.3 OnAttach 驱动 mesh 更新

**版本**：v3.0.3
**日期**：2026-10-27
**状态**：已实现，本地日志与视觉验证通过，待 rudeboybox 复测

> 本文档记录 v3.0.3 相对 v3.0.2 的变更。`docs/Architecture.md` 仍描述 v3.0.2 的架构，**以本文档为准**。背景调查见 `docs/toenail-report-2026-10-27.md`。

---

## 1. 一句话

`OnEquipEvent` 不再调用 `UpdateModelWeight`。mesh 更新改由 `AttachListener` 在 `IAddonAttachmentInterface::OnAttach` 中驱动：当前 mesh 交给 SKEE 的 `BodyMorphInterface::OnAttach`（`isAttaching=true`）用刚就绪的顶点创建 `SHAPEDATA`；其他已存在 mesh 由 `AttachListener` 遍历 `BipedAnim` 调 `ApplyVertexDiff(..., false)`。

---

## 2. 要修复的问题

v3.0.2 下，新 NPC **首次同帧**穿脚趾甲 + 裤袜时，脚趾甲闪烁一瞬后消失。必须先单独穿脚趾甲（“初始化”），之后同帧穿才正常。由 rudeboybox 在 Nexus 报告。

根因：`TESEquipEvent` 派发时 mesh 尚未 attach，`OnEquipEvent` 里调用的 `UpdateModelWeight` 遍历 `bipedData` 会碰到脚趾甲 mesh，`MorphFileCache::ApplyMorph` 的 `!bodyData` 分支（不受 `isAttaching` 保护）用**未就绪的顶点**创建了 `SHAPEDATA`。这份错误的 base 被永久固化，之后每次 `ApplyMorph` 都用它重置，脚趾甲变形消失。

完整调查见 `docs/toenail-report-2026-10-27.md`。

## 4. 关键设计决策

### 4.1 为什么当前 mesh 交给 SKEE 的 `BodyMorphInterface::OnAttach`

SKEE 的 `BodyMorphInterface` 本身也实现了 `IAddonAttachmentInterface`，在 `OnAttach` 中以 `isAttaching=true` 调 `ApplyVertexDiff`。此时 mesh 刚 attach、顶点就绪，`SHAPEDATA` 创建基准正确。SKEE 长期稳定运行反证了这个时机可靠。

我们在 `kPostPostLoad` 通过 `IActorUpdateManager::AddInterface` 注册，必然在 SKEE 自己的观察者之后。`ActorUpdateManager::OnAttach` 按 vector 顺序遍历，我们的回调执行时 SKEE 已完成。所以当前 mesh 不需要我们重复处理。

### 4.2 为什么其他 mesh 用 `ApplyVertexDiff(false)` 而不是 `UpdateModelWeight`

`UpdateModelWeight` 遍历 actor 所有 biped 节点，**包括尚未 attach 的其他 mesh**。如果某个 mesh 还没 attach 但已在 `bipedData` 中（时序窗口），`ApplyVertexDiff(false)` 会走 `!bodyData` 分支用当前顶点创建 `SHAPEDATA`——正是 v3.0.2 的 bug 路径。

`ApplyVertexDiffToWornMeshes` 直接遍历 `bipedData` 中的 `partClone`，只处理已 attach 的 mesh 实例。对 `hasShapeData=false` 的 mesh 跳过（它们各自的 `OnAttach` 会处理），只对 `hasShapeData=true` 的调 `ApplyVertexDiff(false)`。这保证了每次 `false` 调用都基于正确 `SHAPEDATA`。

### 4.3 为什么跳过条件用 FormID 比较而非 `GetWornArmor`

`TESEquipEvent` 期间 `GetWornArmor` 返回旧值（v3.0.2 §7.7 已确认），但 `AttachListener` 直接用 `bipedData` 遍历，当前 mesh 必然在 `bipedData` 中。用 `armor->GetFormID() == a_attachingArmor->GetFormID() && addon->GetFormID() == a_attachingAddon->GetFormID() && isFirstPerson == a_isFirstPerson` 精确排除当前 mesh，不依赖 `GetWornArmor` 的时序行为。

### 4.4 为什么 `OnActorLoaded` 保留 `UpdateModelWeight`

读档时 mesh 已 attach，`SHAPEDATA` 已正确。`UpdateModelWeight` 是确定性兜底，不依赖“引擎是否为读档装备触发 `OnAttach`”这个未验证假设。

## 5. 验证结果

### 5.1 日志

本地跑“新 NPC 首次同帧穿脚趾甲 + 裤袜”，确认：

- `[Equip]` 后不再有 `[Update] UpdateModelWeight`（读档路径的 `[PostLoad]` 除外）
- `[ApplyOther] SKIP current mesh` 出现，FormID 比较正确识别当前 mesh
- `fallback to isAttaching=true` 完全消失
- `hasShapeData=true` 的 mesh 正确走 `ApplyVertexDiff(false)`
- 脚趾甲 attach 时若 SKEE 未初始化，`[ApplyCurrent]` 以 `isAttaching=true` 兜底

### 5.2 视觉

| 场景                           | 结果                              |
| ------------------------------ | --------------------------------- |
| 新 NPC 首次同帧穿脚趾甲 + 裤袜 | 正常                              |
| 先单独穿脚趾甲再穿裤袜         | 正常                              |
| 已穿脚趾甲 + 裤袜，再穿高跟鞋  | 脚趾甲和裤袜响应 `NoHeel=0`，正常 |

## 6. 已知限制

**已存在错误 `SHAPEDATA` 的存档需 NPC 卸载重载才能修复。** v3.0.2 下某些 NPC 的脚趾甲 `SHAPEDATA` 已在错误时机创建。v3.0.3 的 `AttachListener` 不会干预已存在的 `SHAPEDATA`（`if (!bodyData)` 不成立）。这些 NPC 需卸载重载（mesh 重建）才能自动修复。

如果反馈集中，可考虑提供控制台命令手动重置某个 actor 的 `SHAPEDATA`。

其他已知限制同 v3.0.2，见 `docs/Architecture.md` §11。
